- `docs/AI_CONTEXT.md`：最高产品宪章与开发边界。
- `docs/PROJECT_STATUS.md`：当前架构、模块和完成度快照。

2. 开发日志中的“个人建议”是重要产品输入，但不直接等于立即修改指令。

4. 每完成一个里程碑，更新本文件的任务状态和“版本记录”。

6. 未经明确授权，不修改 backend、数据库结构、推荐算法和已有 API 结构。

## 1. 产品定位

项目不是普通旅游网站，也不是 Three.js 技术展示。

核心定位：

> **AI + GIS + 康养决策体验**

完整价值闭环：

```text
全球目的地探索
↓
理解目的地生活与康养条件
↓
填写个人康养需求
↓
获得可翻页的匹配分析
↓
进入推荐目的地的康养线路图
↓
手动规划或与 AI 对话规划
↓
在二维/三维地图中修改路线
↓
获得住宿、餐饮、活动、医疗与预算方案
↓
保存、比较、分享或重新规划
```

产品判断标准：

- 用户得到的是可以辅助真实决策的方案，而不是漂亮但不可执行的页面。
- 每个重要结论都能说明使用了什么数据、数据来自哪里、何时核验。
- AI 不得凭记忆编造地点、价格、道路、医疗能力或康养效果。
- GIS 不只是展示位置，还要支持路线规划、节点编辑和空间约束判断。

### 数据支撑硬规则

1. 国内目的地优先评估高德地图 Web 服务作为 POI 检索、地理编码和道路路径规划数据源。
2. OpenLayers 是二维地图展示与线路编辑层，不自行提供 POI 和道路事实。
3. AI 只能在已检索、已核验的候选数据中筛选、排序和解释，不能创造不存在的 POI。
4. 高德 POI 不能单独证明民宿/餐厅价格、医院能力或康养效果；这些字段必须使用适合其语义的第二来源。
5. 每条 POI、路线和价格数据必须记录供应商、原始 ID、坐标系、采集时间和核验状态。
6. 高德接口能力、配额和数据使用条款可能变化，开始接入和准备发布时都必须重新检查官方文档。

官方入口：

- [高德 Web 服务 POI 搜索](https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch)
- [高德 Web 服务路径规划](https://lbs.amap.com/api/webservice/guide/api/newroute)
- [高德开放平台 Key 创建与管理](https://lbs.amap.com/api/webservice/guide/create-project/get-key)

## 3. 最终产品结构

### Act1｜品牌入口

目标：让用户理解产品价值，并进入全球探索。

状态：已完成，后续仅处理数据真实性和必要维护，不继续增加视觉动画。

### Act2｜全球康养目的地探索

目标：用数字地球建立全球空间认知，用图片和故事发现目的地。

状态：V2 已收口。不得重新加入 Portal、扫描圈、夸张光环、漂浮按钮或无意义特效。

### Act3｜目的地深度体验

目标：帮助用户理解“在这里生活一段时间会怎样”。

核心内容：

- 真实主图与目的地故事。
- 季节体验。
- 日常生活节奏。
- 气候、空气、森林、海拔等环境数据。
- 医疗可达性。
- 预算情景。
- 适合条件与注意事项。
- 数据来源、更新时间和待核验状态。

### Act4｜AI 康养决策中心

目标：完成问卷、推荐、比较和决策。

核心形态：

- PPT 式网页结果报告。
- 最匹配目的地优先。
- 上一页/下一页自然过渡。
- 每个推荐目的地都有“查看康养线路图”入口。
- OpenLayers 地图随目的地平滑切换。
- 最后一页完成横向比较与行动选择。

### Act5｜AI 康养线路工作台

目标：把推荐转化为可执行、可修改的康养旅居路线。

核心能力：

- OpenLayers 二维手动线路绘制。
- 三维路线预览与空间理解。
- AI 引导式康养需求对话。
- AI 自动路线规划。
- 用户在线修改节点和顺序。
- 住宿、餐饮、景点、康养机构与医疗节点。
- 价格、距离、时间、活动强度与数据来源。
- 保存、比较、分享和重新规划。

## 9. M3｜PPT 式网页结果报告

### 目标

把当前“摘要 + 卡片列表”改造成自然翻页的 AI 康养决策演示。

### 页面顺序

1. 第 1 页：最佳匹配目的地，同时展示本次用户条件与数据状态。
2. 第 2～5 页：其余匹配目的地。
3. 最后一页：横向比较、最终建议、数据缺口和下一步行动。

### 每个推荐目的地页

- 排名与匹配度。
- 真实图片、名称和一句话结论。

12. 希望节奏轻松、适中还是丰富？

## 13. M7｜POI、价格与路线数据体系

### 数据来源策略

| 数据类型 | 首选来源 | 补充/核验来源 | AI 权限 |
|---|---|---|---|
| POI 名称、地址、位置、分类 | 高德地图 POI API | 官方机构、商家公开页面 | 只能筛选和解释 |
| 道路距离、时间、可行路径 | 高德路径规划 API | 后续可插拔路线供应商 | 不自行计算 |
| 医院等级、科室、急诊能力 | 政府、卫健部门、医院官网 | 高德仅用于位置与导航 | 不得推断医疗能力 |
| 民宿/酒店价格 | 商家、授权预订数据或人工核验快照 | 高德若返回仅作线索 | 不得补全缺失价格 |
| 餐厅人均价格 | 商家、授权消费数据或人工核验快照 | 高德若返回仅作参考 | 不得表达为成交价 |
| 营业时间、电话 | 高德与商家来源交叉核验 | 人工抽查 | 必须标注更新时间 |
| 康养适配结论 | 结构化事实、用户约束和规则 | RAG 证据 | 可解释，不可创造事实 |

高德是国内 POI 与路径数据的优先供应商，不是所有业务字段的唯一真相来源。供应商通过适配层接入，避免业务模型绑定高德字段。

### POI 类型

- 住宿：民宿、酒店、康养机构。
- 餐饮：餐厅、轻食、清淡餐和特殊饮食。
- 活动：景点、公园、森林、文化场所、温泉和康养项目。
- 医疗：综合医院、专科、急诊、药店。
- 服务：交通、补给、公共服务和无障碍设施。

### POI 最小字段

```json
{
  "id": "poi-dali-001",
  "destination_key": "cn-yunnan-dali-ancient-city",
  "name": "示例节点",
  "category": "lodging",
  "provider": "amap",
  "provider_poi_id": "",
  "coordinate_system": "GCJ02",
  "latitude": 25.0,
  "longitude": 100.0,
  "address": "",
  "opening_hours": "",
  "price_low": 300,
  "price_high": 500,
  "price_unit": "元/晚",
  "price_observed_at": "2026-08-13",
  "activity_intensity": "low",
  "accessibility": [],
  "medical_notes": "",
  "source_url": "",
  "source_publisher": "",
  "fetched_at": "2026-08-13T00:00:00+08:00",
  "verified_at": "2026-08-13",
  "verification_status": "verified",
  "license_scope": "pending_review"
}
```

### 高德接入约束

- Web 服务请求由后端代理，Key 不写入前端仓库或页面源码。
- 使用 POI 搜索或周边搜索获取候选节点，不能把未经筛选的结果直接作为康养推荐。
- 使用路径规划接口获取道路几何、距离和预计时间，AI 不凭经纬度自行估算。
- 保存高德原始 POI ID 和最小审计字段，业务层使用平台自己的稳定 ID。
- 明确高德坐标数据与 Three.js 全球坐标之间的转换和误差策略。
- 缓存周期、持久化范围、展示方式和再分发行为必须符合接入时有效的数据使用条款。
- 配额不足、接口超时或无结果时必须显示数据状态，不能以 AI 内容填补。

### 价格表达规则

- 使用价格区间，不使用虚假精确数字。
- 标注单位：元/人、元/晚、元/次、元/套餐。
- 标注观察日期和适用条件。
- 动态价格必须标注“以商家实时价格为准”。
- 路线预算分为住宿、餐饮、交通、门票和弹性预算。

### 节点详情要求

- 名称、类型、图片和地址。
- 推荐停留时间。
- 对当前用户的适合理由。
- 到下一节点的距离与时间。
- 营业时间与价格区间。
- 无障碍和活动强度。
- 数据来源和核验时间。

**功能开发完成，人工 WebGL 与多视口体验验收待补。** OpenLayers 和 Three.js 现在共同消费 `route-plan` 单一模型，模型包含分天节点、道路分段、GeoJSON、预算状态、AI 约束、选择状态和数据快照时间。二维拖动、排序、加点、删除、AI 改线和高德道路回写会立即通知三维视图；三维点击或逐日播放会反向同步二维节点、列表和详情抽屉。

当前三维是路线空间概览，不是假地形。路线水平位置来自 WGS84；模型明确返回 `elevation.status = unavailable`，所有道路坐标保持在同一平面，并在界面提示“尚无可核验高程，不显示坡度”。节点的轻微垂直抬升仅是可点击视觉符号，不表达海拔。

## 15. M9｜后端、API 与存储规划

### 建议领域对象

## 16. M10｜RAG 与可信证据系统

### 定位

RAG 用于检索非结构化证据，不替代结构化数据库和路线计算。

### 结构化数据库负责

- 经纬度。
- 气候、AQI、海拔和森林等数值。
- 医疗设施属性。
- POI、营业时间和价格快照。
- 距离、时间、路线和预算。
- 用户约束和路线版本。

### RAG 负责

- 政府报告。
- 医院能力说明。
- 交通政策。
- 康养研究资料。
- 目的地规划文件。
- 需要引用原文依据的长篇资料。

### 开发任务

- [x] 建立文档授权、来源和更新时间登记。
- [x] 定义规范化文档、分块、哈希和元数据策略。
- [x] 建立目的地、主题、有效期和发布机构过滤。
- [x] 检索结果返回来源链接、证据段落与检索通道。
- [x] 建立首版检索准确率与拒答测试集。
- [x] 使用 SQLite FTS5 + Qdrant BGE 向量 + RRF 混合检索。
- [x] AI 回答无法获得证据时明确拒答。

### 不应立即使用 RAG 的场景

- [x] RAG 失败返回证据不足，不污染结构化事实。

### M10 核心 v1 结论（2026-08-20）

**核心后端与向量数据库完成，语料覆盖和前端产品化仍在 M10 内继续。** 开发环境使用 Qdrant 本地持久化 collection，正式嵌入为 `BAAI/bge-small-zh-v1.5` 512 维中文向量；SQLite schema v2 保存规范化来源、分块与 FTS5 关键词索引，检索层通过 RRF 合并关键词和向量排序。

**M10 产品功能阶段完成。** Act3 已增加可信依据工作台，PPT 结果页每个目的地均可打开证据抽屉；前端通过统一 API 发起追问并固定使用本地 RAG。回答显示来源段落、发布机构、核验日期和原始链接，证据不足时明确拒答。
